## 1. 개요

### 1.1 배경

동영상 상세 조회처럼 특정 데이터에 읽기 요청이 집중되는 상황에서는 데이터베이스가 반복 조회의 병목이 될 수 있습니다. 특히 캐시가 비어 있거나 만료된 시점에 동시에 많은 요청이 유입되면 다수의 요청이 데이터베이스를 함께 조회하는 Cache Stampede가 발생할 수 있습니다.

### 1.2 목적

이 프로젝트는 Redis 캐시 적용 전후의 동영상 단건 조회를 같은 로컬 환경에서 비교하고, Cache Stampede 방지 전략이 데이터베이스 부하를 줄이는지 검증하는 Spring Boot 기반 실습 환경입니다.

### 1.3 범위

**포함 범위**

- 회원과 동영상의 생성 및 조회 REST API.
- `GET /videos/{id}`의 Redis 읽기 모델 캐싱.
- 신선 캐시, stale-while-revalidate, 분산 Lock, 음수 캐시, Redis 장애 폴백.
- `VIDEO_CACHE_ENABLED`를 통한 캐시 적용 전후 비교.
- k6 동시 요청 시험과 Prometheus·Grafana 관측.

**제외 범위**

- 사용자 인증과 권한 관리.
- 동영상 수정·삭제, 조회 수·좋아요 수 변경.
- 다중 인스턴스 운영 배포와 자동 확장.
- 장기 성능 이력 저장, 알림, CI 기반 정기 부하 시험.

## 2. 목표와 성공 지표

### 2.1 목표

1. 캐시 미스와 만료 시점의 동시 요청이 데이터베이스로 몰리는 현상을 재현합니다.
2. Redis 캐시와 Lock을 적용했을 때 데이터베이스 조회 수 감소를 측정합니다.
3. 캐시 장애가 발생해도 동영상 조회가 데이터베이스 폴백으로 계속 동작함을 확인합니다.
4. 애플리케이션, MySQL, Redis 지표를 하나의 로컬 관측 환경에서 확인합니다.

### 2.2 성공 지표

| 지표 | 성공 기준 | 측정 방법 |
| --- | --- | --- |
| 동시 요청 성공 | k6의 200개 동시 `GET /videos/{id}`가 모두 HTTP 200을 반환 | k6 check |
| DB 조회 증가량 | 캐시 비활성 시 200, 활성 시 1 | `video_find_by_id_db_load_total` 차이 |
| 응답 시간 비교 | 같은 환경·시나리오에서 `http_req_duration` p95를 비교 기록 | k6 요약 |
| 장애 복원력 | Redis 접근 실패 시 DB 조회 결과를 반환 | 서비스 단위 테스트 |

`p95`는 실행 머신과 Docker 상태의 영향을 받으므로 고정 통과 기준이 아니라 비교 지표로 사용합니다.

## 4. 기능 요구사항

### P0. 도메인 API

#### FR-001. 회원 생성과 조회

사용자는 회원을 생성하고 목록 또는 식별자로 조회할 수 있어야 합니다. 존재하지 않는 식별자를 조회하면 HTTP 404를 반환해야 합니다.

#### FR-002. 동영상 생성과 조회

사용자는 기존 회원을 작성자로 지정해 동영상을 생성하고, 목록 또는 식별자로 조회할 수 있어야 합니다. 존재하지 않는 회원으로 생성하거나 존재하지 않는 동영상을 조회하면 HTTP 404를 반환해야 합니다.

### P0. 캐시 보호

#### FR-003. 동영상 단건 조회 캐시

동영상 단건 조회는 JPA 엔티티가 아닌 동영상 상세 DTO를 JSON으로 Redis에 저장해야 합니다. 신선한 캐시 값은 데이터베이스 조회 없이 즉시 반환해야 합니다.

#### FR-004. Cache Stampede 방지

캐시 미스에서는 하나의 요청만 Lock을 획득해 데이터베이스를 조회하고 캐시를 채워야 합니다. Lock을 획득하지 못한 요청은 최대 1초 동안 캐시 채움을 기다린 뒤, 시간이 초과되면 데이터베이스 조회로 대체해야 합니다.

#### FR-005. stale-while-revalidate

신선 기간이 지난 캐시 값은 stale 기간 동안 즉시 반환해야 합니다. 이때 Lock을 획득한 요청 한 건만 비동기 갱신을 예약해야 합니다.

#### FR-006. 음수 캐시와 장애 폴백

존재하지 않는 동영상은 짧은 TTL로 음수 캐시해야 합니다. Redis 읽기·쓰기·Lock 처리 실패는 조회 실패로 전파하지 않고 데이터베이스 조회로 대체해야 합니다.

### P0. 비교와 관측

#### FR-007. 캐시 on/off 비교

환경 변수 `VIDEO_CACHE_ENABLED`로 같은 애플리케이션에서 Redis 캐시 사용 여부를 바꿀 수 있어야 합니다. 기본값은 캐시 사용입니다.

#### FR-008. 부하 시험과 지표

전용 시드 SQL과 k6 시나리오는 stale 상태의 동일 동영상에 200개 동시 요청을 보내야 합니다. 애플리케이션은 DB 상세 조회 횟수 지표를 제공해야 하며, Prometheus와 Grafana는 주요 상태를 표시해야 합니다.

## 5. 비기능 요구사항

| 구분 | 요구사항 |
| --- | --- |
| 성능 | 캐시 활성화 시 정상적인 Lock 대기 시간 안에 200개 동시 stale 조회의 DB 조회 증가량이 1이어야 합니다. |
| 가용성 | Redis가 일시적으로 이용 불가해도 동영상 단건 조회는 데이터베이스 폴백으로 제공되어야 합니다. |

| 보안 | 비밀번호는 환경 변수로만 설정하며 기본값은 로컬 개발에만 사용합니다. |

## 6. 제약사항과 가정

- 로컬 Docker 환경에서 MySQL, Redis, Prometheus, Grafana를 실행합니다.
- 애플리케이션은 기본적으로 로컬 호스트의 MySQL과 Redis에 연결합니다.
- 부하 시험 전에 대상 회원과 동영상이 시드 SQL로 준비되어 있어야 합니다.
- 동영상 상세 조회의 정상 DB 응답 시간은 Lock 대기 제한인 1초 이내라고 가정합니다.
- 이 문서는 현행 구현의 기준 문서이며 이후 기능 로드맵을 정의하지 않습니다.
